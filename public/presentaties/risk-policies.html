Microsoft Entra ID Protection × Conditional Access

Two risk policies.
Two different questions.

Sign-in risk asks: is this specific sign-in really the user? User risk asks: is this identity already compromised? ID Protection calculates both scores, but only a Conditional Access policy turns them into action. Flip the toggle to see the difference.

per authentication

Sign-in risk policy

“Is this sign-in really Eva?”

Scored in real time for each authentication, using signals such as anonymous IPs, unfamiliar sign-in properties and malicious IPs. It catches the moment a correct password is used by the wrong person.

The legitimate user simply passes MFA and the risky sign-in closes itself. The attacker with only a password gets no token.

per identity

User risk policy

“Is Eva’s account compromised?”

Aggregated over time from detections such as leaked credentials, password spray and threat intelligence. Where the next sign-in comes from doesn’t matter; the account itself is the problem.

Require risk remediation forces a secure password change, or reauthentication for passwordless users, and revokes existing sessions. A stolen password and stolen tokens both stop working.

Why you want both

They cover different moments in the same attack. Sign-in risk stops the attempt at the door; user risk cleans up an identity that may already be in someone else’s hands. Without either, ID Protection is a reporting tool and someone in the SOC has to notice, investigate and reset by hand.

Before you turn them on

Risk-based policies need Microsoft Entra ID P2. Users must have an MFA method registered before risk hits them, so pair this with an MFA registration policy. Start in report-only mode. Require risk remediation doesn’t work for guests and external users, since Entra can’t revoke their sessions. The legacy risk policies inside ID Protection were retired on 1 October 2026, so Conditional Access is now the only place these policies live.
